# 014 - 后端服务重新集成方案

## 概述

由于 Cloudflare Worker 的出站 IP 被 Google Gemini API 地理限制拦截，本方案将验证链路改为：
- **客户端** → **Worker（RSA 加密）** → **后端服务（海外部署）** → **Gemini API**

这样利用后端的海外部署环境，绕过地理限制。

## 架构设计

### 通信流程

```
┌─────────────────┐
│   游戏客户端     │
│  (Cocos Creator) │
└────────┬────────┘
         │ 明文 JSON: {"word": "CAT"}
         │ POST /w-game-service/api/v1/word/verify
         ▼
┌─────────────────────────────────────────┐
│   Cloudflare Worker（边缘）             │
│   1. 读取请求体（明文）                 │
│   2. 导入 RSA 公钥（硬编码）           │
│   3. 使用 RSA-OAEP-SHA256 加密         │
│   4. 将密文放入 X-Encrypted-Payload 头 │
│   5. 转发到后端                        │
└────────┬────────────────────────────────┘
         │ 加密请求头: X-Encrypted-Payload: <Base64 密文>
         │ POST http://elvis1949.top:9100/api/v1/word/verify
         ▼
┌─────────────────────────────────────────┐
│   后端服务（海外，Python FastAPI）      │
│   1. 从 X-Encrypted-Payload 头读取密文  │
│   2. 使用 RSA 私钥解密（private.pem）   │
│   3. 检查时间戳、Nonce 防重放           │
│   4. 从 Redis 缓存查询                 │
│   5. 若缓存未命中，调用 Gemini API     │
│   6. 返回 JSON: {"valid": bool, ...}   │
└────────┬────────────────────────────────┘
         │ 响应: JSON
         │ HTTP 200
         ▼
┌─────────────────┐
│   游戏客户端     │
│  显示结果        │
└─────────────────┘
```

### 关键设计要素

#### 1. **RSA 加密（Worker 端）**
- **公钥源**：`src/backend/public.pem`
- **格式**：SPKI DER Base64
- **算法**：RSA-OAEP-SHA256
- **实现位置**：`tools/cloudflare/worker.js` 中的 `encryptRsaOaep()` 函数
- **密钥传输**：通过 `X-Encrypted-Payload` 头

#### 2. **RSA 解密（后端）**
- **私钥源**：`src/backend/private.pem`
- **中间件**：`src/backend/middleware/rsa_decrypt.py`
- **容错机制**：
  - 时间戳验证（±90秒）
  - Nonce 防重放（Redis 存储）
  - 自动降级（Redis 不可用时允许通过）

#### 3. **长连接支持**
- **三层支持**：
  - 客户端 ↔ Worker：自动 Keep-Alive
  - Worker ↔ 后端：fetch() 默认支持
  - 后端 ↔ Gemini：httpx AsyncClient 配置了连接池
- **连接复用**：减少建立新连接的开销

#### 4. **缓存策略**
后端采用多层缓存（已有，无需改动）：
- **L1**：进程内 LRU（8000 词条）
- **L2**：Redis 全局缓存（1 年过期）
- **缓存键**：统一大写 `word:UPPER(WORD)`
- **TTL**：365 天（可配）

## 常见问题

### Q1: 为什么 Worker 需要硬编码公钥？
- **A**：避免客户端额外的 `/api/public-key` 请求，减少网络往返。密钥本身是公开的，hardcoding 无安全风险。

### Q2: RSA-OAEP 加密会不会造成性能问题？
- **A**：否。RSA-2048 加密的耗时在 10-50ms 范围内，相对整体请求的 300-900ms 可忽略。

### Q3: 如果后端不可用，游戏还能玩吗？
- **A**：客户端会降级：
  1. 使用本地 L2 缓存（localStorage）
  2. 如果配置了本地词库，使用本地验证
  3. 网络失败时返回 `valid=false`，游戏继续

### Q4: 如何更新后端 Gemini prompt？
- **A**：修改 `src/backend/word_validator.py` 的 `call_gemini_api()` 函数中的 `prompt` 变量，重启后端服务。

### Q5: 为什么要使用 RSA 而不是 HMAC？
- **A**：
  - HMAC 需要共享密钥，不适合公开部署
  - RSA 公钥可以公开分发，私钥仅在后端保存
  - OAEP 提供更强的安全性（避免 padding oracle 攻击）

## 安全考虑

### 密钥管理
- ✓ 公钥在 Worker 中硬编码（无安全风险）
- ✓ 私钥仅在后端存储（文件权限 600）
- ✓ API Key 通过环境变量注入（不出现在代码中）

### 防护机制
- ✓ 时间戳验证（±90秒，防止重放）
- ✓ Nonce 验证（Redis 存储，防重放）
- ✓ 请求头验证（Cloudflare 提供的 CF-Connecting-IP 等）

### 降级策略
- Redis 不可用 → 内存 LRU 缓存
- Gemini 失败 → dictionaryapi.dev（如后端实现了）
- 后端失败 → 本地缓存 + 游戏继续

## 性能指标（预期）

| 场景 | 耗时（p50） | 耗时（p95） | 备注 |
|------|-----------|-----------|------|
| L1 缓存命中（内存） | < 1ms | < 5ms | 最快路径 |
| L2 缓存命中（localStorage） | 5-10ms | 20-30ms | 本地持久化 |
| Redis 缓存命中 | 50-100ms | 100-150ms | 后端内存 |
| Gemini 调用（优化后） | 500-700ms | 700-900ms | 网络外呼 |
| 加密开销（Worker） | 10-50ms | 50-100ms | 可接受 |

## 回滚方案

如果后端出现问题，可快速回滚到直连 Gemini 的 Worker：
1. 修改 Worker 代码，恢复 `/gemini/generate` 路由
2. 修改 NetworkService，恢复 `BASE_URL = 'https://ai.elvis1949.cloudns.pro/gemini'`
3. 重新部署（预计 5-10 分钟）
