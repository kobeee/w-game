# 单词验证接口简化与加密优化方案

> **文档版本**: v1.0  
> **更新时间**: 2025-10-29  
> **适用范围**: 微信小游戏客户端 · Cloudflare Worker · FastAPI 后端

---

## 1. 现状与主要痛点

- **接口401频发**：现有“双阶段（/config → /verify）+ 签名”方案流程复杂，任一环节时间戳或签名计算误差都会触发401，导致客户端重试、体验下降。
- **耗时超标**：验证一次需要多次网络往返（小游戏 → Worker → 后端 → Gemini），同时每轮要做签名校验、动态密钥拉取等冗余操作，长尾延迟被拉高到 >800 ms。
- **加解密链路脆弱**：客户端本地脚本生成的对称密钥和签名算法实现复杂，容易出现计算误差或与后端实现不一致的问题。
- **交互轮次冗余**：小游戏端在输入第1个字母时就发起远程校验，既浪费请求次数，也让玩家看到“验证中”闪烁。

---

## 2. 方案目标

1. **单接口直连**：客户端直接 `POST /api/v1/word/verify`，取消配置拉取环节。
2. **公私钥加解密**：采用非对称加密（RSA-OAEP-SHA256），客户端硬编码公钥，加密后的载荷通过HTTPS发送；后端持有私钥解密即可。
3. **请求内容自描述**：密文中包含单词、时间戳、随机串等字段，后端解密后即可完成格式校验、重放防护。
4. **性能目标**：50p99 ≤ 350 ms、90p95 ≤ 450 ms；缓存命中情况下 ≤ 120 ms。
5. **交互约束**：客户端本地校验输入长度 ≥3 个字母后再发请求，后端再做一次兜底校验。

---

## 3. 新接口整体架构

```
微信小游戏
  ├─ 本地长度校验(≥3) + 词频缓存
  ├─ 使用RSA公钥加密 payload(JSON)
  └─ POST /api/v1/word/verify
           │
           ▼
Cloudflare Worker (现有防护保留)
  ├─ 限流 & 日志 & Header 注入
  └─ 转发至后端，仅允许 Cloudflare IP
           │
           ▼
FastAPI 后端 (Gunicorn/Uvicorn)
  ├─ 使用私钥解密 → 验证字段 → 防重放
  ├─ 多级缓存 (Redis/内存) 命中判定
  └─ 未命中则调用 Gemini → 写入缓存
```

- **单接口对外**：`POST https://api.xxx.com/api/v1/word/verify`
- **鉴权方式**：密文解密 + 时间戳窗口（±90 s）+ nonce 防重放；保留 Cloudflare 源IP白名单。

---

## 4. 加解密与载荷设计

### 4.1 算法选型

- **算法**：RSA-2048 + OAEP 填充（SHA-256 摘要，MGF1 with SHA-256）。
- **理由**：
  - 对短文本加密延迟低（<1 ms），易与微信小游戏/Node/Cloudflare 环境兼容。
  - OAEP 可有效抵御选择密文攻击，比 PKCS#1 v1.5 更安全。
  - 客户端仅持有公钥，无需担心秘钥泄露；后端私钥放在受控环境即可。

### 4.2 密钥管理

| 项目 | 内容 |
|------|------|
| 私钥生成 | `openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out private.pem`
| 公钥导出 | `openssl rsa -pubout -in private.pem -out public.pem`
| 服务部署 | 私钥写入后端安全目录（仅服务用户可读），读取后放入内存；公钥硬编码在小游戏 & 运维文档。
| 版本标记 | 使用 `key_id`（例如 `2025Q4-01`）写入配置，密文 JSON 内附带，便于滚动升级。
| 轮换策略 | 新旧私钥并行 7 天：后端维护 `active_keys` 字典；客户端版本发布后在下一次发版时切换公钥。

### 4.3 密文载荷（加密前JSON）

```json
{
  "word": "STACK",
  "client_ts": 1730186400123,
  "nonce": "7b4f0f86-0d90-4df0-97f1-2c8e9c1beaf0",
  "client_id": "wx-miniapp",
  "key_id": "2025Q4-01"
}
```

- `word`：只接受 A-Z 字母，统一转大写。
- `client_ts`：毫秒时间戳；后端容忍 ±90 s，超时返回 40101。
- `nonce`：客户端随机 UUID，后端放入 Redis（TTL 120 s）防重放。
- `client_id`：用于灰度、统计，可用于区分平台（小游戏/内部工具）。
- `key_id`：匹配后端私钥；未知 `key_id` 直接 40102。

> **注意**：客户端仍需在加密前做本地校验：① 字母长度 ≥3；② 仅字母字符；③ 空格和特殊字符拒绝。

### 4.4 加密流程

1. 客户端将上述 JSON 字符串化，并使用 UTF-8 编码。
2. 使用硬编码的 `public.pem` 执行 RSA-OAEP 加密，得到字节流。
3. 将密文进行 Base64 编码，得到可传输字符串。
4. 构造请求体：`{"ciphertext": "...", "key_id": "2025Q4-01"}`。
   - `key_id` 冗余放在外层，便于后端在解密前选对私钥。
5. 通过 HTTPS 发送至后端。

### 4.5 后端解密与校验

1. 根据外层 `key_id` 获取对应私钥。
2. Base64 解码得到密文字节流，使用 RSA-OAEP 解密。
3. 解析 JSON 并执行：
   - 格式校验：字段齐全、类型正确、单词 ≥3 个字符且全字母。
   - 时间戳校验：`abs(now - client_ts) ≤ 90 s`。
   - 重放校验：`nonce` 是否在 Redis 中出现；若已存在则返回 40103。
4. 校验通过后进入业务判断流程。

## 5. 验证接口设计

### 5.1 请求

```
POST /api/v1/word/verify
Content-Type: application/json
CF-Connecting-IP: <Cloudflare 自动注入>
CF-Ray: <Cloudflare 自动注入>

{
  "ciphertext": "MIIB...",
  "key_id": "2025Q4-01"
}
```

### 5.2 响应

```json
{
  "request_id": "2025-10-29-9f1c",
  "valid": true,
  "definition": "猫",
  "source": "cache",  // cache | gemini | fallback
  "latency_ms": 108,
  "word": "CAT",
  "checked_at": "2025-10-29T12:00:31.482Z"
}
```

- `request_id`：后端生成用于日志跟踪。
- `source`：命中来源；供运营观察缓存覆盖率。
- `latency_ms`：后端内部耗时，便于前端做埋点对齐。
- 错误时返回：

```json
{
  "request_id": "2025-10-29-ff45",
  "error_code": 40102,
  "message": "invalid key id"
}
```

### 5.3 错误码草案

| Code | HTTP | 描述 | 处理建议 |
|------|------|------|----------|
| 40101 | 401 | 客户端时间戳超出窗口 | 客户端同步系统时间或重启小游戏 |
| 40102 | 401 | `key_id` 未识别 | 检查客户端公钥版本 |
| 40103 | 401 | nonce 重复/请求重放 | 触发安全日志；客户端重试需换 nonce |
| 40010 | 400 | 解密后数据格式不合法 | 检查客户端请求构造 |
| 42201 | 422 | 单词长度 <3 或包含非法字符 | 前端应拦截；记录异常行为 |
| 42901 | 429 | 触发速率限制 (Worker/后端) | 维持当前限额，提示稍后重试 |
| 500xx | 500 | 后端内部错误（Gemini/Redis） | 兜底返回“稍后重试”并告警 |

## 6. 性能优化要点

- **请求轮次裁剪**：小游戏端只保留本地缓存 + 单次远程验证，取消 `/config` 调用。
- **输入拦截**：本地字母长度判定（≥3）与常见无效词缓存（如 `AAA`）；避免无意义远端调用。
- **缓存优先**：
  - 内存 LRU（最近 5k 词）命中即返回，预计覆盖率 70%。
  - Redis 共享缓存命中率预计 90%+，异步刷新 TTL 30 天。
  - Gemini 仅在缓存未命中时调用，并将结果写入缓存。
- **异步合并**：对同一 `word` 的并发请求在后端做单飞（single flight），避免并发打满 Gemini。
- **连接复用**：Worker → 后端走 HTTP/2，后端调用 Gemini 使用 `aiohttp` 连接池，减少建连开销。
- **监控阈值**：p95 延迟 >500 ms 连续 5 分钟触发报警。

---

## 7. 安全与可观测性

- 保留 Cloudflare 白名单、速率限制与安全日志能力。
- 后端新增以下日志：`request_id`、解密状态、错误码、来源 IP、word 长度、耗时。
- 将 `401xx/422xx` 计入安全告警面板，识别潜在脚本攻击。
- Redis 中存储 `nonce` 时设置 `EX 120`，并在 key 中包含 `client_id`，方便定位问题。
- 定期（每日）统计：总请求数、缓存命中率、Gemini 调用量与成本。

## 8. 业务流程（文字版）

1. 玩家在小游戏中选择字母拼出单词。
2. 客户端检测总长度；若 `<3`，直接提示“继续输入，不触发远程”。
3. 满足条件后，构造 JSON 载荷并进行 RSA 加密，携带 `nonce` 与当前时间戳。
4. 发送到 Worker，Worker 进行速率限制后转发。
5. 后端解密并执行：
   - 字段/格式校验 → 时间戳/nonce → 单词规范化。
   - 查询本地缓存 → Redis → Gemini。
6. 返回验证结果，客户端根据 `valid` 决定是否消除卡牌。
7. 若返回错误码，客户端按表格处理并埋点统计。

## 9. curl 验证指引

> 目的：便于调试或联调时验证接口是否工作正常。

1. **准备公钥文件**（与客户端一致）：保存在 `public.pem`。
2. **构造明文 JSON**（保存为 `payload.json`）：

```json
{"word":"stack","client_ts":1730186400123,"nonce":"7b4f0f86-0d90-4df0-97f1-2c8e9c1beaf0","client_id":"wx-miniapp","key_id":"2025Q4-01"}
```

3. **使用 OpenSSL 加密并转为 Base64**：

```bash
openssl pkeyutl -encrypt -pubin -inkey public.pem -in payload.json \
  -pkeyopt rsa_padding_mode:oaep -pkeyopt rsa_oaep_md:sha256 -pkeyopt rsa_mgf1_md:sha256 | base64 > ciphertext.b64
```

4. **调用接口**（将密文放入 `ciphertext` 字段）：

```bash
curl -X POST https://api.xxx.com/api/v1/word/verify \
  -H "Content-Type: application/json" \
  -d "{\"ciphertext\": \"$(tr -d '\n' < ciphertext.b64)\", \"key_id\": \"2025Q4-01\"}"
```

5. **观察响应**：若返回 `valid` 字段，说明链路正确；若出现 `401xx`，按错误码提示排查。

## 11. 风险与缓解

- **密钥泄露风险**：若怀疑公钥被篡改，立即轮换 `key_id` 并强制客户端升级；对老版本请求通过 `key_id` 分类限流。
- **Gemini 限额耗尽**：缓存命中率不足时可能触发限额，需监控并准备备用模型或本地词库降级。
- **时间同步问题**：客户端设备时间不准会触发 40101，需在小游戏里提示“同步系统时间后重试”。
- **性能回退**：发布后需重点观察 p95 延迟，若未达标，优先排查缓存命中与 Worker 限流配置。

---

## 12. 结论

该方案以“单接口 + 非对称加密”替换原有多轮交互和复杂签名逻辑，显著降低 401 触发概率，并通过本地拦截、缓存与速率限制控制整体耗时。curl 指引可帮助开发快速定位问题，后续只需按推进计划实施并做好监控，即可在保证安全性的前提下降低调用成本、提升玩家体验。
