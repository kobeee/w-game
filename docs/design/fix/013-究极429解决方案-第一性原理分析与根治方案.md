## 一、第一性原理分析

### 1.1 什么是429错误？

HTTP 429 Too Many Requests 是服务器的速率限制响应。**本质上是客户端在单位时间内发起的请求数超过了服务器允许的阈值**。

要从根源解决429，必须回答两个核心问题：
1. **谁在发起请求？** - Cocos引擎的下载器
2. **为什么会超限？** - 并发请求数超过了微信平台的限制

### 1.2 微信小游戏的硬性限制（官方文档）

根据[微信小游戏官方网络文档](https://developers.weixin.qq.com/minigame/dev/guide/base-ability/network.html)：

| API | 并发上限 | 说明 |
|-----|---------|------|
| wx.request | 10 | HTTP请求 |
| wx.uploadFile | 10 | 文件上传 |
| wx.downloadFile | 10 | 文件下载 |
| **以上三者共享** | **10** | **总并发上限** |
| wx.connectSocket | 5 | WebSocket |

**关键洞察**：`wx.request` + `wx.uploadFile` + `wx.downloadFile` 三者**共享10个并发槽位**，不是各自10个。

### 1.3 Cocos Creator下载器的真实行为

根据[Cocos Creator 3.8官方文档](https://docs.cocos.com/creator/3.8/manual/en/asset/downloader-parser.html)，assetManager的下载器有以下预设：

```javascript
// Cocos Creator 3.x 默认预设
{
    'default': { priority: 0 },
    'preload': { maxConcurrency: 2, maxRequestsPerFrame: 2, priority: -1 },
    'scene':   { maxConcurrency: 8, maxRequestsPerFrame: 8, priority: 1 },
    'bundle':  { maxConcurrency: 8, maxRequestsPerFrame: 8, priority: 2 },  // ⚠️ 问题根源
    'remote':  { maxRetryCount: 4 },
    'script':  { priority: 2 }
}
```

**问题根源**：`bundle` 预设的 `maxConcurrency: 8`，这意味着：
- 加载一个Bundle时，引擎会**同时发起最多8个HTTP请求**
- 如果同时加载2个Bundle，就是 8 × 2 = 16 个并发请求
- 而微信的总上限是10，**直接超限触发429**

### 1.4 Bundle加载的请求拆解

当调用 `assetManager.loadBundle('bundleName')` 时，引擎实际会发起以下请求：

1. **GET `config.json`** - Bundle配置清单（必需）
2. **GET `index.js`** - Bundle脚本（如有）
3. **可能的import map** - 依赖映射

每个Bundle至少2-3个HTTP请求。假设Loading阶段加载5个Bundle（bg/title/tiles/slot/words），理论上至少需要 5 × 2 = 10 个请求，**刚好触碰微信并发上限**。

但问题不止于此。当PreloadManager在加载Bundle后继续加载内部资源（SpriteFrame/JsonAsset）时：

```
Bundle加载: 5个Bundle × 2请求 = 10请求
资源加载: 5个Bundle × 平均3个关键资源 = 15请求
───────────────────────────────────────
总计: 25请求（远超10个并发限制）
```

**即使串行加载Bundle**，如果内部资源预加载使用并发，仍然会触发429。

## 二、现有方案为何失效

### 2.1 方案010/011/012的根本缺陷

| 方案 | 做法 | 缺陷 |
|------|------|------|
| 010 (ZIP化) | 将Bundle打包成ZIP | 未修改引擎底层并发控制，仍会触发429 |
| 011 (轻量级) | PreloadManager串行加载 | 只控制了Bundle层，未控制引擎preset |
| 012 (终极) | 全局单例队列 | 仍然依赖应用层控制，引擎底层无感知 |

**核心问题**：所有方案都是在**应用层**做控制，但**引擎底层的downloader.preset**仍然保持默认的高并发配置。

```
应用层控制: PreloadManager (MAX_CONCURRENT_DOWNLOADS = 3)
      ↓
引擎层: assetManager.loadBundle() → 内部使用 preset['bundle'].maxConcurrency = 8
      ↓
平台层: wx.downloadFile() → 总并发上限 10
      ↓
结果: 应用层控制被引擎层绕过，429触发
```

### 2.2 当前代码的实际问题

查看 `PreloadManager.ts`，当前实现：

```typescript
// 第17-18行
private readonly MAX_CONCURRENT_DOWNLOADS = 3; // 应用层限制
private readonly DOWNLOAD_QUEUE_DELAY = 200;   // Bundle间延迟
```

这个控制**只对PreloadManager管理的任务有效**，但：

1. **引擎内部的并发控制不受影响** - `assetManager.loadBundle()` 仍然使用 `preset['bundle'].maxConcurrency = 8`
2. **Bundle内部资源加载不受控制** - 每个Bundle加载完成后，`bundle.load()` 调用会触发额外的并发请求
3. **其他模块绕过PreloadManager** - MainMenu、GameApp等模块直接调用 `assetManager.loadBundle()`

## 三、第一性原理解决方案

### 3.1 核心策略：从源头控制并发

**不是控制应用层，而是直接控制引擎层的preset配置**。

```typescript
// 在游戏启动时（main.ts或LoadingScene.onLoad），直接修改引擎预设
assetManager.presets['bundle'].maxConcurrency = 2;      // 降至2
assetManager.presets['bundle'].maxRequestsPerFrame = 2;
assetManager.presets['default'].maxConcurrency = 2;
assetManager.presets['remote'].maxConcurrency = 2;
```

这样无论任何模块调用 `assetManager.loadBundle()`，引擎内部都会遵守2并发的限制。

```typescript
/**
 * 配置微信小游戏环境下的引擎下载参数
 * 必须在任何 loadBundle 调用之前执行
 */
function configureAssetManagerForWechat(): void {
    if (typeof wx === 'undefined') {
        console.log('[EngineConfig] 非微信环境，保持默认配置');
        return;
    }

    console.log('[EngineConfig] 配置微信小游戏下载参数...');

    // 🔥 核心修改：将引擎并发限制降至微信安全阈值
    // 微信总并发上限10，预留2个给其他API（如网络验证），游戏下载使用8个
    // 但为安全起见，设置为4，分散到多个队列中

    const WECHAT_SAFE_CONCURRENCY = 2;  // 单队列并发数
    const WECHAT_REQUESTS_PER_FRAME = 2; // 每帧最大请求数

    // 修改Bundle加载预设（最关键）
    if (assetManager.presets['bundle']) {
        assetManager.presets['bundle'].maxConcurrency = WECHAT_SAFE_CONCURRENCY;
        assetManager.presets['bundle'].maxRequestsPerFrame = WECHAT_REQUESTS_PER_FRAME;
    }

    // 修改默认预设
    if (assetManager.presets['default']) {
        assetManager.presets['default'].maxConcurrency = WECHAT_SAFE_CONCURRENCY;
        assetManager.presets['default'].maxRequestsPerFrame = WECHAT_REQUESTS_PER_FRAME;
    }

    // 修改场景加载预设
    if (assetManager.presets['scene']) {
        assetManager.presets['scene'].maxConcurrency = WECHAT_SAFE_CONCURRENCY;
        assetManager.presets['scene'].maxRequestsPerFrame = WECHAT_REQUESTS_PER_FRAME;
    }

    // 修改远程资源预设
    if (assetManager.presets['remote']) {
        assetManager.presets['remote'].maxConcurrency = WECHAT_SAFE_CONCURRENCY;
        assetManager.presets['remote'].maxRetryCount = 5; // 增加重试次数
    }

    // 直接修改下载器全局配置（兜底）
    if (assetManager.downloader) {
        (assetManager.downloader as any).maxConcurrency = WECHAT_SAFE_CONCURRENCY * 2; // 全局上限4
        (assetManager.downloader as any).maxRequestsPerFrame = WECHAT_REQUESTS_PER_FRAME;
    }

    console.log('[EngineConfig] ✅ 微信小游戏下载参数配置完成');
    console.log('[EngineConfig] bundle.maxConcurrency:', assetManager.presets['bundle']?.maxConcurrency);
}
```

**修改 `preloadBundleGroup` 方法**：

```typescript
private async preloadBundleGroup(bundles: {name: string, priority: number}[], startProgress: number, endProgress: number): Promise<void> {
    const totalBundles = bundles.length;
    if (totalBundles === 0) return;

    const progressPerBundle = (endProgress - startProgress) / totalBundles;

    // 🔥 所有环境都使用串行加载（保证稳定性）
    console.log('[PreloadManager] 使用严格串行Bundle加载');

    for (let i = 0; i < totalBundles; i++) {
        const bundle = bundles[i];
        const bundleStartProgress = startProgress + i * progressPerBundle;
        const bundleEndProgress = bundleStartProgress + progressPerBundle;

        // 加载单个Bundle
        await this.preloadSingleBundle(bundle.name, bundleStartProgress, bundleEndProgress);

        // Bundle间添加自适应延迟
        if (i < totalBundles - 1) {
            const delay = this.getAdaptiveDelay(this.BUNDLE_DELAY_MS);
            await new Promise(resolve => setTimeout(resolve, delay));
        }
    }
}
```

## 五、关键技术细节解析

### 5.1 为什么是 maxConcurrency = 2？

```
微信总并发上限: 10
├─ 游戏下载使用: 8（预留2个给网络验证等）
├─ Bundle加载队列: 2个并发
├─ 资源加载队列: 2个并发
├─ 其他请求预留: 4个
└─ 实际峰值并发: 2 + 2 = 4（安全阈值）
```

设置为2而不是4的原因：
1. **引擎内部有多个队列**：Bundle队列、资源队列、场景队列可能同时活跃
2. **安全边际**：预留更多空间给意外请求
3. **防止抖动**：网络波动时，2并发更稳定

### 5.2 为什么Bundle间需要延迟？

即使并发设为2，如果Bundle连续触发，仍可能出现：

```
t=0:   Bundle A 发起请求1、请求2
t=1ms: Bundle B 发起请求3、请求4（此时A还未完成）
t=2ms: Bundle C 发起请求5、请求6
结果: 6个并发请求同时在途
```

添加300ms延迟后：

```
t=0:     Bundle A 发起请求1、请求2
t=100ms: Bundle A 请求1完成
t=200ms: Bundle A 请求2完成
t=300ms: Bundle B 发起请求3、请求4（此时A已完成）
结果: 峰值并发永远不超过2
```

### 5.3 为什么超时设为15秒而非30秒？

1. **用户体验**：30秒等待太长，用户会认为App卡死
2. **微信平台限制**：小游戏进入后台5秒后网络请求会中断
3. **降级策略**：15秒足够加载核心资源，其他资源可延迟加载
4. **数据支撑**：正常网络下，5个Bundle+核心词库加载应在10秒内完成

## 七、降级策略

### 7.1 加载失败降级

```typescript
// 在PreloadManager中
private async preloadSingleBundle(bundleName: string, ...): Promise<void> {
    try {
        await this.attemptBundleLoad(bundleName, ...);
    } catch (error) {
        console.warn(`[PreloadManager] ${bundleName} 加载失败，启用降级`);

        // 非核心Bundle直接跳过
        if (!this.isCriticalBundle(bundleName)) {
            console.log(`[PreloadManager] ${bundleName} 非核心资源，跳过`);
            return;
        }

        // 核心Bundle重试3次
        for (let i = 0; i < 3; i++) {
            await new Promise(r => setTimeout(r, 1000 * (i + 1)));
            try {
                await this.attemptBundleLoad(bundleName, ...);
                return;
            } catch (e) {
                console.warn(`[PreloadManager] ${bundleName} 第${i+1}次重试失败`);
            }
        }

        // 最终失败，标记使用本地缓存
        console.error(`[PreloadManager] ${bundleName} 彻底失败，使用缓存`);
    }
}

private isCriticalBundle(bundleName: string): boolean {
    return ['bg', 'words'].includes(bundleName);
}
```

## 十一、总结

本方案从**第一性原理**出发，深入分析了429错误的根源：

1. **问题本质**：Cocos引擎的`preset['bundle'].maxConcurrency = 8`超过了微信`wx.downloadFile`的`10`并发上限
2. **解决策略**：在引擎层直接修改preset配置，而非在应用层做控制
3. **核心价值**：从源头控制并发，彻底根治429

**关键改动**：
```typescript
// 一行代码根治429
assetManager.presets['bundle'].maxConcurrency = 2;
```

**相比之前方案的优势**：
- 010 (ZIP化)：复杂度高，需要改构建流程 → 本方案仅需修改运行时配置
- 011 (轻量级)：应用层控制无法约束引擎 → 本方案直接修改引擎配置
- 012 (终极)：依赖全局单例管理 → 本方案让引擎自动遵守限制

**实施成本**：
- 代码改动：~120行
- 实施时间：1小时
- 风险等级：低
- 回滚难度：极易
