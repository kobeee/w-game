# 016-究极熔断与流量整形方案：从第一性原理彻底解决 429 (Circuit Breaker Strategy)

**创建日期**: 2025-11-25
**状态**: 已实施 (v1.2)
**优先级**: P0 (Critical)

---

## 一、 核心复盘：为什么之前的方案还会 429？

经过深入的第一性原理分析，我们发现之前的方案（014/015）存在根本性的逻辑漏洞：

1.  **死循环攻击 (Death Spiral)**：
    *   当服务器返回 429 时，意味着"IP 暂时被封"。
    *   旧方案的反应是：`立即重试` 或 `延迟 1秒重试`。
    *   **服务器视角**：这个 IP 刚被封，又发来请求（重试的）-> **延长封禁时间**。
    *   **结果**：客户端越重试，服务器封得越久，形成死循环。

2.  **QPS 超标 (Rate Limit)**：
    *   旧方案仅限制了 **并发数 (Concurrency)** 为 4。
    *   但如果这 4 个请求处理很快（例如小 JSON 文件），客户端可能在 1秒内发出 40 个请求。
    *   Cloudflare 等 WAF 防火墙不仅看并发，更看 **QPS (每秒请求数)**。瞬时高频请求是典型的攻击特征。

3.  **虚假的 100% (Fake Completion)**：
    *   为了防止卡死，旧方案允许资源加载失败后继续。
    *   **结果**：Loading 界面跑到了 100%，跳转 Main 场景时，因为缺失资源（Config/JSON），Cocos 引擎发起新的请求去下载。
    *   此时网络仍在 429 封禁中，新的请求瞬间失败，导致游戏崩溃或白屏。

## 二、 016 方案：第一性原理的解法

我们引入了微服务架构中常见的 **熔断器模式 (Circuit Breaker)** 和 **流量整形 (Traffic Shaping)**。

### 2.1 核心策略

1.  **全局熔断 (Global Pause)**
    *   **规则**：一旦检测到 **任意一个** 429 错误，拦截器立即进入 `PAUSED` 状态。
    *   **行为**：暂停调度器 2000ms。在此期间，**所有**排队中的请求（无论优先级）全部冻结，一个都不发。
    *   **目的**：让服务器"冷静"，彻底解除 IP 封禁。

2.  **流量整形 (Rate Limiting)**
    *   **规则**：强制两次请求发送的物理间隔至少 `100ms`。
    *   **效果**：即使并发设为 3，最大 QPS 也被物理锁定在 10 左右。这远低于大多数 WAF 的触发阈值。

3.  **真实反馈 (Strict Error Handling)**
    *   **规则**：资源加载失败就是失败，**绝不**假装成功。
    *   **行为**：Loading 场景捕获到错误后，不再强制跳转，而是弹出模态对话框，引导用户手动点击"重试"。

## 三、 实施细节 (Implementation Details)

### 3.1 `WXNetworkGate.js` (v1.2)
已更新至 `tools/inject-gate.js` 和 `src/cocos/assets/scripts/util/WXNetworkGate.ts`。

*   **并发数**: 降至 **3** (安全值)。
*   **请求间隔**: **100ms** (强制流控)。
*   **熔断时间**: **2000ms** (遇到 429 全局暂停)。

```javascript
// 核心熔断逻辑
if (res.statusCode === 429) {
    console.error(`[WXGate] 🚨 触发 429！启用熔断机制，全局暂停 ${COOL_DOWN_TIME}ms`);
    _isPaused = true; // ⛔️ 停止一切活动
    setTimeout(() => {
        _isPaused = false; // ✅ 恢复
        _scheduler();
    }, COOL_DOWN_TIME);
    // ... 重试逻辑 ...
}
```

### 3.2 `LoadingScene.ts`
已重构，移除了所有"超时强制跳转"的逻辑。

*   **严格模式**: `ensureBundleLoaded` 和 `preloadCriticalAssets` 失败会直接抛出异常。
*   **用户交互**: 捕获异常后，调用 `wx.showModal` 显示重试弹窗。

```typescript
try {
    await this.preloadManager.ensureBundleLoaded(bundleName);
    // ...
} catch (error) {
    this.showRetryDialog(); // 🛑 弹窗让用户重试，而不是崩溃
}
```

### 3.3 `LoadingUI.ts`
已重构为纯粹的 View 组件。

*   移除了内部的 `startLoading` 驱动逻辑。
*   移除了 30秒 强制跳转。
*   公开了 `updateProgress` 方法供 Scene 调用。
*   保留了"防止倒车"和"文案屏蔽"的视觉优化。

## 四、 验证方法 (Verification)

1.  **观察日志**:
    *   在微信开发者工具或真机调试中，如果出现 429，控制台应打印：
        `[WXGate] 🚨 触发 429！启用熔断机制，全局暂停 2000ms`
    *   随后的 2秒内，**不应有任何新的请求发出**。

2.  **观察加载速度**:
    *   由于增加了 100ms 间隔，加载条应该会匀速前进，不会出现"瞬间跑完"的情况。

3.  **断网测试**:
    *   断网后，Loading 条应停止。
    *   恢复网络后，点击弹出的"重试"按钮，进度条应归零并重新开始。

## 五、 总结

016 方案不再试图"绕过"限制，而是**尊重**网络规则。通过**熔断**来保护 IP 信誉，通过**限流**来避免触发防火墙，通过**严格错误处理**来保证游戏运行时的稳定性。这是解决 429 顽疾的终极方案。
